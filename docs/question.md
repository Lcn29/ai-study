## 一、Tokenizer：切分与编号

### 问题 1：Tokenizer 返回 Token ID，还是 Token 与 Token ID？

**问题：**

第 01 课中，在实际实现中，一段话经过 Tokenizer 时，得到的是 Token ID
（Token 只是内部计算的一个中间结果），还是 Token + Token ID？

**答案：**

实际送进生成模型的，通常是 Token ID 序列；Tokenizer 是否同时返回 Token，要看具体接口。
一段话通常对应多个 ID，并非只有一个。

这里要分清“概念上的转换过程”和“接口返回什么”：

```text
概念过程：文字 → 确定 Token 边界 → 映射为 Token ID
接口返回：可以只返回 ID 序列，也可以同时提供 Token 和 ID
```

沿用第 01 课的教学例子：

```text
输入文字：猫吃鱼
确定的 Token：［猫］［吃］［鱼］
对应的 ID：[7, 12, 25]
```

如果接口只返回 `[7, 12, 25]`，也已经表达了这次切分结果：每个 ID 都指向词表中对应的 Token，
顺序和重复位置也保留着。模型随后用这些 ID 查 Embedding 表，无需再接收一份 Token 文本。

所以，第一种理解更接近模型输入时的情况，但“Token 只是内部计算的一个中间结果”需要调整：
**Token 是切分得到的单元，Token ID 是该单元的编号表示。**

实现不一定先构造一份可读的 Token 字符串列表，再生成 ID；文档这样分步，是为了讲清两者的关系。
具体库是否同时返回二者，需要查看它的接口。

### 问题 2：为什么通常只把 Token ID 交给模型？

**问题：**

既然 Tokenizer 能确定 Token 与 Token ID，为什么模型计算时通常只需要接收 Token ID？

**答案：**

因为词表已经确定了 Token 与 ID 的对应关系，而模型下一步只需要用 ID 查出向量，
同时传 Token 文本没有额外作用。

沿用文档中的教学例子：

```text
Tokenizer 输出：[7, 12, 25]
                     ↓ 按 ID 查 Embedding 表
模型取得：     [猫的向量, 吃的向量, 鱼的向量]
```

这样设计有三个直接好处：

1. **省去重复信息。** 在同一词表中，`7` 已经确定指向“猫”，再传一份“猫”不会增加信息。
2. **方便计算。** 整数序列便于组织成张量，执行批量查表；Token 对应的文本或字节片段长度则不固定。
3. **职责清楚。** Tokenizer 负责文字与编号之间的转换，模型负责查表和后续数值计算。
   模型生成编号后，也由 Tokenizer 解码回文字。

可以类比后端传递用户 ID：下游已经能按 ID 取得所需数据，就不必每次同时传一份用户名。

Token 文本仍然有用：展示切分边界、调试分词结果时，人需要看它。
所以接口可以提供 Token 和 ID 两者，但模型计算通常只需要 ID。

### 问题 3：Tokenizer 的词表存储 Token → Token ID 的映射，对吗？

**问题：**

也就是 Tokenizer 内部有一张词表，存储着 Token → ID 的映射关系？

**答案：**

对，可以这样理解：**Tokenizer 使用一张词表，记录 Token → Token ID 的映射关系。**

沿用文档的教学词表：

| Token | Token ID |
| --- | --- |
| 猫 | 7 |
| 吃 | 12 |
| 鱼 | 25 |

但它还需要切分规则，才能确定输入文字应该对应哪些 Token：

```text
输入文字 → 按规则切分 → 按词表取得 ID
猫吃鱼   → ［猫］［吃］［鱼］ → [7, 12, 25]
```

所以，**词表负责“对应哪个编号”，切分规则负责“怎样划分单元”**。
解码时再按编号查回对应单元，并按解码规则还原文字。

这里是概念结构；具体实现未必把词表存成一个独立的映射对象。

## 二、Token Embedding：从编号到初始向量

### 问题 4：模型的 Token Embedding 表是 Token ID → 向量，对吗？

**问题：**

第 02 课中写着模型也保存一张 Token Embedding 表，这种表是 Token ID → 向量，这个是对的吗？

**答案：**

对，**第 02 课讲的 Token Embedding 表，就是用 Token ID 查出对应的初始向量。**

两张表的职责可以连起来看：

| 由谁使用 | 对应关系 | 作用 |
| --- | --- | --- |
| Tokenizer 的词表 | Token → Token ID | 给切分单元编号 |
| 模型的 Token Embedding 表 | Token ID → 初始向量 | 取得模型计算的起点 |

沿用第 02 课的教学数据：

```text
ID 1 → [1, 0, 2]
ID 4 → [0, 2, 1]
ID 5 → [1, 1, 0]
```

实际存储通常是一张矩阵：Token ID 用来索引行，每一行存放一个向量。
这些向量属于模型参数，可以在训练中被更新。

在同一张固定表中，相同 ID 查出的初始向量相同；
后续经过位置与上下文计算，得到的 Hidden State 可以不同。

以上对应文档讨论的普通 Token Embedding，未核对某个具体模型的实现。

### 问题 5：为什么不由 Tokenizer 直接把 Token 映射成初始向量？

**问题：**

那么为什么不这样设计：Tokenizer 就存储一张 Token → 初始向量的表，
然后将初始向量直接给模型，模型不需要表？

**答案：**

可以这样设计。只要取出的向量完全一致，后续计算也一致，模型就可以从这些初始向量继续计算。
但这相当于把 Embedding 层移到了 Tokenizer 一侧，表本身仍然存在。

通常把它留在模型里，主要有三个原因。

#### 1. 这张表需要参与模型训练

Tokenizer 的切分规则和编号确定后，语言模型训练仍然需要调整初始向量，使它们更适合后续计算：

```text
Token ID → Embedding 查表 → 后续计算 → 预测误差
                  ↑                    │
                  └── 训练时更新向量 ──┘
```

如果表放在 Tokenizer 中，训练过程就需要跨到 Tokenizer 一侧更新它，
并同步保存这张表与模型的版本。把它作为模型参数统一管理更直接。

#### 2. 传编号比传整组向量更紧凑

每个输入位置只需要传一个整数 ID；如果提前查表，就要传这个位置的全部向量坐标。

特别是 Tokenizer 在 CPU、模型在 GPU 的部署中，可以先把紧凑的 ID 序列交给 GPU，
再从已经位于 GPU 的 Embedding 表里取向量，减少需要搬运的输入数据。

#### 3. 切分规则与学到的表示，可以分别管理

即使两个模型使用完全相同的词表和编号，它们训练出的 Embedding 向量也可以不同：

```text
同一个 Token ID
    ├─ 模型甲的表 → 模型甲学到的向量
    └─ 模型乙的表 → 模型乙学到的向量
```

如果向量放进 Tokenizer，Tokenizer 就还需要绑定具体模型的权重版本。

因此，这个方案在计算上可行；常见设计把边界放在 ID 这里，是为了让 Tokenizer 管切分与编号，
让模型统一管理可训练参数和数值计算。
对后续计算层来说，它最终收到的本来就是 Embedding 层输出的向量。

这里解释设计取舍，未核对具体框架；不能据此认定某个模型接口支持直接输入向量。

## 三、Softmax：从分数到概率

### 问题 6：减去最大值后，各自取指数是怎样计算的？

**问题：**

第 03 课《输出再输入：模型怎样逐步生成下一个 Token》中，下面两步的计算过程是怎样的？

```text
减去最大值2：[0, −1, −2, −3]
各自取指数： [1, 0.367879, 0.135335, 0.049787]
```

**答案：**

#### 1. 先认识“取指数”

这里的“取指数”就是计算 $e^x$，其中 $e$ 是一个固定的数学常数：

$$
e \approx 2.718281828
$$

`exp(x)` 就是 $e^x$ 的另一种写法。

#### 2. 每项减去最大值

原分数为 `[2, 1, 0, −1]`，每个分数都减去最大值 `2`：

```text
2 − 2    =  0
1 − 2    = −1
0 − 2    = −2
(−1) − 2 = −3
```

于是得到 `[0, −1, −2, −3]`。

#### 3. 对每项取指数

把其中每个数字作为 $e$ 的指数。计算要用两条规则：

**任何非零数的零次方等于 1；负整数次方等于对应正整数次方的倒数。**

| 输入 $x$ | 计算过程 | 结果（约） |
| --- | --- | --- |
| `0` | $e^0=1$ | `1` |
| `−1` | $e^{-1}=\frac{1}{e}=\frac{1}{2.718281828}$ | `0.367879` |
| `−2` | $e^{-2}=\frac{1}{e^2}=\frac{1}{7.389056099}$ | `0.135335` |
| `−3` | $e^{-3}=\frac{1}{e^3}=\frac{1}{20.085536923}$ | `0.049787` |

所以：

```text
[0, −1, −2, −3]
        ↓ 每一项计算 e 的该次方
[1, 0.367879, 0.135335, 0.049787]
```

#### 4. 除以总和，得到概率

到这里得到的还不是概率。再把每项除以它们的总和，才完成 Softmax：

```text
总和 ≈ 1 + 0.367879 + 0.135335 + 0.049787
     ≈ 1.553002

第一项概率 ≈ 1 ÷ 1.553002 ≈ 0.643914
```

展示数值经过四舍五入，计算时应保留更多精度。
