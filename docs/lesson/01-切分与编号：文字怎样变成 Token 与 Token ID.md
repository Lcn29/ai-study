# 切分与编号：文字怎样变成 Token 与 Token ID

你在输入框里写下一句话，模型接下来会收到什么？

在本课讨论的文本处理流程中，文字先经过一个转换程序：它按照既定规则切出片段，再把这些片段映射为整数编号。这个程序叫 **Tokenizer，分词器**；切出的单元叫 **Token，词元**；对应的编号叫 **Token ID，词元编号**。[^转换]

先把整条路径放在眼前：

```mermaid
flowchart LR
    A["原始文字"] --> B["Tokenizer：按规则切分"]
    B --> C["Token：切出的单元"]
    C --> D["按词表查编号"]
    D --> E["Token ID：整数序列"]
    E --> F["下一小节：查出初始向量"]
```

本文对应《AI学习目录》第一阶段“文字怎样进入模型”中的第 01 课“Token 是小片段，ID 是编号”，目标依据《32课学习设计与掌握目标》中该课的要求。读完并独立完成练习后，你应能做到四件事：

1. 把原始文字、Token 和 Token ID 分开，并按顺序解释转换。
2. 解释为什么字数、单词数和 Token 数不能直接画等号。
3. 说明编号大小没有“更重要”或“语义更接近”的保证。
4. 区分 BPE 训练时学习合并规则，和使用时应用已经学好的规则。

你不需要会 Python，也不需要先懂向量、矩阵或概率。本文的切分、词表与编号都是教学约定；它们用来说明步骤，不是对真实模型分词结果的测量。

## 一、把一句话拆成三种对象

### 第一步：先有原始文字

课程用这句话开始：

```text
猫吃鱼
```

此时我们只有一段人可以阅读的文字，还没有指定 Token 边界，也没有编号。

为了演示，课程**假设**它被切成三个单元：

```text
［猫］［吃］［鱼］
```

每一对方括号里是一个 Token。方括号只是标出边界，不属于输入文字。

这组切法是本例的前提。不能因此推断所有模型都会把“猫吃鱼”切成这三个 Token。实际边界要看具体分词器及其规则。[^课程]

### 第二步：给每个 Token 查编号

分词器使用一张**词表**。词表记录有哪些 Token，以及它们各自对应哪个 ID。沿用课程的教学约定：

| 教学 Token | Token ID |
| --- | --- |
| 猫 | 7 |
| 吃 | 12 |
| 鱼 | 25 |

于是这次转换的结果是：

```text
原始文字：猫吃鱼
Token：  ［猫］［吃］［鱼］
Token ID：[7, 12, 25]
```

注意三个对象之间的区别：

| 对象 | 本例中的样子 | 它回答什么问题 |
| --- | --- | --- |
| 原始文字 | `猫吃鱼` | 用户写了什么？ |
| Token 序列 | `［猫］［吃］［鱼］` | 按当前规则分成哪些单元？ |
| ID 序列 | `[7,12,25]` | 每个单元对应词表里的哪个编号？ |

**Token 是单元，ID 是这个单元的编号**。把“猫”的编号写成 `7`，不等于“猫”的含义就是数字七。

### 顺序保留，重复出现也保留

沿用同一教学切法和词表，如果文字变成“猫吃鱼猫”，结果就是：

```text
［猫］［吃］［鱼］［猫］
→ [7, 12, 25, 7]
```

这里一共四个 Token，也有四个 ID 位置。虽然只出现了三种不同 Token，重复的“猫”仍然占一个位置。

因此，“这次序列有多少个 Token”和“词表里有多少种 Token”是不同问题。数本次 Token 数量时，要数序列里的位置，不能只数不同种类。

### 编码与解码，各沿哪个方向走？

把文字转换为 ID 序列，叫**编码**。从 ID 查回对应单元，再还原文字，叫**解码**。它们在文本输入和输出中承担相反方向的转换。[^转换]

例如，在本例的简单约定下：

```text
[7, 12, 25]
→ ［猫］［吃］［鱼］
→ 猫吃鱼
```

这只验证本例的查回过程。真实分词器还可能处理字节、规范化和特殊 Token；这里不据简单拼接宣称所有编码、解码都逐字无损。

## 二、为什么 Token 数不能直接按字数算？

“猫吃鱼”刚好有三个汉字，本例也刚好切成三个 Token。这个结果来自教学规则，不能变成“一个汉字总是一个 Token”的通用公式。

Token 的边界由分词器决定。它可以对应一个字符、一个完整单词，也可以对应单词的一部分；实际字节级单元还未必能单独显示为完整字符。[^粒度]

### 用一个英文单词看清楚粒度

原始资料用 `unpredictable` 举例。它有 13 个英文字母，可以用两种**教学切法**来比较：

```text
按字符：
［u］［n］［p］［r］［e］［d］［i］［c］［t］［a］［b］［l］［e］
共 13 个单元

按资料中的子词示例：
［un］［predict］［able］
共 3 个单元
```

文字没有变，采用的切分方式变了，单元数量就变了。这里没有调用某个真实模型；不能据此宣布某模型一定把这个词切成三个 Token。[^粒度]

这种把词拆成较小片段的方式叫 **Subword，子词切分**。子词片段可以较长，也可以很短；它们不必严格对应语言学上的词根或词缀。Token 并不要求恰好等于人认定的“一个词”。

### 换了分词器，需要重新检查结果

不同分词器可能有不同的词表、切分规则和特殊 Token 处理方式，所以同一段文字的 Token 数可能不同。即使两个结果碰巧数量相同，也不能据此认定它们的边界和编号相同。[^绑定]

因此，面对真实问题：

> 这段话在我使用的模型里有多少个 Token？

你需要明确所用模型及其配套分词器，检查实际编码结果。仅凭“多少字”“多少单词”或本文的示意切法，不能给出精确答案。

想亲手观察实际切分，可以打开 [OpenAI Tokenizer](https://platform.openai.com/tokenizer)，输入一段文字。记录时，把所用 Tokenizer 或编码方案的名称、完整输入和输出编号一起保存；比较两个结果时，先确认输入中的空格和换行也相同。本文的教学编号不用于对照工具输出。

## 三、ID 是地址，数字大小没有语义排名

在教学词表中，“鱼”的 ID 是 `25`，“猫”的 ID 是 `7`。我们可以确定它们对应不同的词表条目，但不能从 `25>7` 推出“鱼更重要”。

同样，`12` 与 `7` 相差 `5`，`25` 与 `12` 相差 `13`，也不能据此说“猫和吃的含义更接近”。**编号的数值距离，没有语义距离的保证**。[^转换]

你可以把 ID 想成查表地址：地址用于找到条目，不负责给条目的含义打分。下一小节才会根据 ID 查出用于计算的初始向量。

还有一个容易混的地方：ID 与输入位置各管一件事。

| 本例中的信息 | 含义 |
| --- | --- |
| ID `7` | 当前教学词表中“猫”的编号 |
| 第一个位置 | 这个 Token 在本次序列中的先后位置 |
| 第四个位置也是 ID `7` | “猫”又出现了一次，仍查同一词表条目 |

词表编号只在相应词表中解释。真实模型与其分词器存在配套关系，不能把另一套分词器的 ID 原样换进去，假定它们仍代表相同单元。[^绑定]

## 四、BPE 怎样学会切分，又怎样处理新文字？

现在还剩一个问题：切分规则从哪里来？

课程用 **BPE，Byte Pair Encoding，字节对编码**说明一种常见做法：在训练材料中反复统计相邻单元，合并高频的一对，记录合并规则；使用时按既有规则处理新文字。这里用字符做小算例，帮助理解合并过程，不实现完整字节级分词器。[^合并]

先把两个阶段分开：

| 阶段 | 输入什么 | 做什么 | 得到什么 |
| --- | --- | --- | --- |
| 训练分词器 | 一批训练文字及其频次 | 统计相邻对，选高频对合并，再重新统计 | 词表与有先后次序的合并规则 |
| 使用分词器 | 一段新文字、已确定的词表和规则 | 按规则优先次序合并适用的相邻单元，再查 ID | 当前文字的 Token 与 ID 序列 |

**输入一句新话，是应用规则的过程**。普通使用不会因为发现新组合，就重新训练分词器或临时增加合并规则。

训练分词器也要与训练语言模型分开：前者确定这里的切分与编号体系，后者学习后续的向量和预测参数。学会给文字分块，不等于已经学会回答问题。[^合并]

### 先把教学设置写完整

沿用课程设置，基础符号有：

```text
a、b、c、d、·
```

`·` 是本例人为规定的词尾标记，用来表示一个词到这里结束。它不是原词中的字母，也不表示真实模型都使用这个标记。

基础符号 `d` 预先包含在表中，尽管下面的训练词里没有它。这个前提很重要：稍后遇到新词 `abd` 时，我们才有办法表示其中的 `d`。

训练材料只有两类词：

| 训练词 | 出现次数 | 初始拆分 |
| --- | --- | --- |
| `ab` | 2 | `a、b、·` |
| `abc` | 1 | `a、b、c、·` |

想象展开后的三份材料：

```text
第一份：a b ·
第二份：a b ·
第三份：a b c ·
```

我们只演示两轮合并；没有继续训练。[^课程]

### 第一轮：统计相邻的两项

“相邻”是紧挨着。例如 `a b c ·` 中的相邻对是 `(a,b)`、`(b,c)`、`(c,·)`。`a` 和 `c` 中间隔着 `b`，不算一对。

把三份材料的次数加起来：

| 相邻对 | 怎样数 | 总次数 |
| --- | --- | --- |
| `(a,b)` | 两份 `ab` 各一次，加一份 `abc` 的一次 | 3 |
| `(b,·)` | 两份 `ab` 各一次 | 2 |
| `(b,c)` | 一份 `abc` 中的一次 | 1 |
| `(c,·)` | 一份 `abc` 中的一次 | 1 |

最高频的是 `(a,b)`。记录第一条规则：

```text
规则 1：a + b → ab
```

这里的 `+` 表示相邻符号合并，不是数字相加。应用合并后，训练材料变成：

```text
ab  × 2：［ab］［·］
abc × 1：［ab］［c］［·］
```

**出现次数要算进统计**。不能因为表里只写了两行，就只给 `(a,b)` 数两次。

### 第二轮：先重新统计，再选最高频对

经过上一轮合并，单元已经变了。`a、b` 成了一个整体 `ab`，因此不能沿用旧的相邻对计数。

新的统计是：

| 相邻对 | 总次数 |
| --- | --- |
| `(ab,·)` | 2 |
| `(ab,c)` | 1 |
| `(c,·)` | 1 |

最高频的是 `(ab,·)`。记录第二条规则：

```text
规则 2：ab + · → ab·
```

合并后：

```text
ab  × 2：［ab·］
abc × 1：［ab］［c］［·］
```

在这组教学规则下，`ab` 编码时占一个 Token；`abc` 仍占三个 Token。词尾标记如果尚未合并，也算本例中的一个单元。

到这里，训练停止，留下按顺序排列的两条规则：

```text
1. a + b → ab
2. ab + · → ab·
```

本例每轮的最高频项都唯一，不涉及并列时如何选择。真实训练的停止条件与并列处理，需要读对应实现；不能从这个小表补出通用规则。

### 使用阶段：新词 `abd` 只应用这两条规则

新输入是 `abd`。先按本例基础符号拆开，并补词尾标记：

```text
［a］［b］［d］［·］
```

应用规则 1：`a` 与 `b` 相邻，可以合并：

```text
［ab］［d］［·］
```

再检查规则 2：它要求 `ab` 与 `·` 相邻。这里中间隔着 `d`，所以不能合并。

最终 Token 序列是：

```text
［ab］［d］［·］
```

这个新词没有因为人看着像一个完整词，就自动获得整词 Token。也没有新建 `ab+d→abd` 规则。**使用阶段只应用已经确定的规则，并检查它们是否适用**。

### 切分完成，再查出 ID

课程为这个英文小算例单独规定了一张词表：

| 教学 Token | ID |
| --- | --- |
| `a` | 0 |
| `b` | 1 |
| `c` | 2 |
| `d` | 3 |
| `·` | 4 |
| `ab` | 5 |
| `ab·` | 6 |

它与前面中文例子的词表是两套教学设置，不能混用。于是：

```text
abd
→ ［a］［b］［d］［·］
→ ［ab］［d］［·］
→ [5, 3, 4]
```

查回时：

```text
[5, 3, 4]
→ ［ab］［d］［·］
→ abd·
→ 按本例约定移除词尾标记
→ abd
```

请留意，我们始终在做三件分开的事：**按规则确定单元，按词表取得编号，按解码约定还原文字**。

## 六、参考答案与达标标准

### 检查 1 的答案

```text
原始文字：鱼吃猫猫
Token：  ［鱼］［吃］［猫］［猫］
Token ID：[25, 12, 7, 7]
```

一共有四个 Token 位置，三种不同 Token。重复的“猫”仍然占位置，两个位置的 ID 都是 `7`。

下一小节会根据每个 ID 从 Token Embedding 表中取出初始向量。ID 在这里是查表地址；不需要在本节计算向量。

**过关点**：转换顺序正确，单元和编号分开，重复位置没有丢失。

### 检查 2 的答案

这个推断把字数当成了 Token 数。实际切分由具体分词器及其规则决定，一段文字可能按不同粒度表示，数量不一定等于字数。

要确认精确数量，需要确定实际模型与配套分词器，再检查该文本的真实编码结果。两个结果数量相同，只说明数量相同；边界和 ID 仍要分别核对。

**过关点**：能说明为什么不能仅按字数算，并指出应该读取哪种实际结果。

### 检查 3 的答案

两种说法都不能仅凭 ID 推出。编号负责索引当前词表条目；它没有重要性排名或语义距离的保证。

编号必须结合对应词表解释。换词表后，同一个数不保证仍指向同一个 Token，因此不能只搬运 ID、忽略分词器与模型的配套关系。

**过关点**：能用“查表地址”说明用途，不为编号大小附加语义结论。

### 检查 4 的答案

```text
abcd
→ ［a］［b］［c］［d］［·］
→ 应用规则 1
→ ［ab］［c］［d］［·］
→ 规则 2 不适用
→ [5, 2, 3, 4]
```

第二条规则要求 `ab` 与 `·` 相邻，这里被 `c、d` 隔开，所以不能使用。

当前只是使用已经固定的分词器，没有重新统计训练材料，也没有学习新的合并规则。因此不能根据“这是一个词”临时创建整词 Token。

训练阶段做“统计→合并→重算→记录规则”；使用阶段做“按已有规则处理新输入→查词表编号”。

**过关点**：步骤与 ID 正确，能解释相邻条件、固定规则，以及训练和使用的区别。

### 还想检查是否会独立推演？

沿用相同英文规则，把 `ab`、`abc`、`abd` 分别编码，并解释为什么只有第一个在本例中成为一个 Token。

对照结果：

| 输入词 | 最终 Token | ID 序列 | 本例 Token 数 |
| --- | --- | --- | --- |
| `ab` | `［ab·］` | `[6]` | 1 |
| `abc` | `［ab］［c］［·］` | `[5,2,4]` | 3 |
| `abd` | `［ab］［d］［·］` | `[5,3,4]` | 3 |

三个词都能应用第一条规则；只有 `ab` 中合并后的 `ab` 与词尾标记紧挨着，能继续应用第二条规则。

文章提供的是学习与验收路径。实际掌握要靠你独立完成转换、解释反例和推演新输入来确认。

## 七、可选进阶：把小算例与真实分词器分开

### 基础符号覆盖，是组合新词的前提

本例能表示 `abd`，一个必要前提是 `d` 已经属于基础符号。没有整词 Token，不妨碍用已知小单元组合；但如果某个基础符号本身也没有，就需要按具体实现处理，不能凭空给它新增编号。

完整的字节级基础表提供另一种覆盖路径。此时字符可以由多个字节表示，单个 Token 不一定能独立显示成一个完整汉字或符号。这就是“Token 不是固定一个字符”的另一个原因。[^课程]

这一节无需手算 UTF-8 字节。开始使用真实分词器时，再读取它采用的基础单元和字节处理方式。

### 真实流程还可能包含其他步骤

真实分词器可能包含规范化、预分词、字节处理、合并、编号映射及特殊 Token 处理。不同实现的流程需要分别核对。本文只把核心转换拆成可观察的教学步骤，没有覆盖完整生产实现。[^课程]

例如，本例规定移除词尾标记才能还原原词。这是我们已经写明的解码约定，不能拿去处理另一个分词器里的标记。

### 文本 Token 数与请求计量，各有核对对象

给一段文字重新分词，可以得到该编码操作的结果。真实模型请求还可能包含系统规则、历史消息、工具定义等内容；响应的计量也不能一概由最终可见字符串重新分词代替。[^计量]

因此，当你要核对窗口占用或费用时，应查看实际请求组成和服务返回的对应统计，而不能把“这句话切成几个 Token”直接当成整次请求的账本。具体计费留到后续课程，不在这里推算固定比例。

## 带着编号继续下一小节

现在，你应该能够把过程讲完整：

> 分词器先按规则把文字表示成 Token 序列，再按词表查出对应 ID。Token 的粒度由具体规则决定；ID 是编号，不是语义分数。BPE 在训练时统计并学习合并规则，使用时应用已有规则处理新输入。

接下来阅读《表示与计算：从 Token ID 到 Embedding 与隐藏状态》，就可以继续回答“整数编号怎样变成模型能计算的一组数”。

若要回看文字编码、模型输入与输出解码的链路，可参阅 [Codex里token是啥？文字是如何变成token的](https://www.bilibili.com/video/BV1LjTX6ZEJV)；BPE 的训练和使用过程可参阅 [Hugging Face 官方 BPE 课程](https://huggingface.co/learn/llm-course/en/chapter6/5)。
