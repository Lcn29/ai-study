# 第七阶段串讲：从工具请求到按观测推进任务

助手说：“我去读取规则乙。”下一条消息却没有文件内容，只是一句“我再确认一下”。又过了几轮，它告诉用户可以退货。

这几句话看起来像在工作，但我们还不知道：谁真正读了文件，读到了什么，失败是否被回传，最后的判断依据又从哪里来。

第七阶段“从聊天到工具执行”包含第19课“Function Calling与MCP”、第20课“ReAct与Plan-And-Execute”。前一课建立一次请求、执行和回传的闭环，后一课让闭环根据真实观测继续，并在外层计划需要改变时重规划。

本文沿同一组设备规则走完这个过程：先读取一份材料，再在发现过期、遇到超时、取得原文和收到新事实时决定下一步。第五阶段的证据范围、第六阶段的独立验收，会贯穿整条执行链。

最低前置知识是知道任务有输入、依据与成功条件；正文会补齐这些内容，不要求安装SDK或Agent框架。规则、日期、教学工具与运行轨迹都是课程设定，不是实际制度或业务服务。下面讲的是应用拥有并调度的普通工具，以及经MCP连接的服务工具；平台托管工具的具体执行位置需按对应接口另外核对。

## 一、先明确问题与动作范围

用户先提出一个只读任务：

> 2025-06-12提出申请，购买设备签收第10天，未拆封，有含订单号的电子凭证，能申请退货吗？只依据甲乙丙解释，不创建记录、不执行退款。

签收当天计第0天，按申请日期判断规则版本。材料的信息如下：

| 材料 | 发布与生效信息 | 范围 |
| --- | --- | --- |
| 甲 | 2024-12-20发布；2025-01-01至2025-05-31生效 | 旧版购买退货 |
| 乙 | 2025-05-20发布；2025-06-01起生效，明确替代甲的购买规则 | 新版购买退货 |
| 丙 | 2025-06-10发布并生效 | 租用归还，不修改乙 |

完整条款是：

| 条款 | 教学原文 |
| --- | --- |
| 甲1 | 购买设备在签收后第 0—7 天、未拆封，可以申请退货。 |
| 甲2 | 需要纸质发票；电子订单截图不能代替纸质发票。 |
| 乙1 | 购买设备在签收后第 0—14 天、未拆封，可以申请退货。 |
| 乙2 | 凭证可以是纸质发票，或含订单号的电子凭证；聊天截图不属于上述凭证。 |
| 乙3 | 已拆封设备不能按乙1申请退货，只能转维修核验；转维修不代表已经批准退款。 |
| 丙1 | 租用设备应在签收后第 0—30 天归还。 |
| 丙2 | 本规则不适用于购买设备退货，也不修改乙的购买规则。 |

读者在本文中能看到全部材料。后面的模拟中，模型当前可见的内容则取决于应用实际送回了什么。正文展示乙2，不等于某次读取超时的模型已经收到乙2。

主问题应该适用乙，第10天、未拆封和含订单号电子凭证分别由乙1、乙2支持，结论只到符合展示的申请条件。现在用工具取得这些依据，而不是让模型只凭名字猜内容。

## 二、一次“读取乙”，先是请求，后来才是执行

课程明确设计一个教学工具，名称为“读取教学条款”，唯一业务参数为“材料编号”，只允许甲、乙、丙。它说明本次可以请求什么，不是某个现成SDK的函数名。

例如，请求乙的业务参数可以表示为：

```json
{"材料编号": "乙"}
```

这段只展示教学参数，不是一份完整模型API请求。参数结构的约定常称为Schema：它可以限制字段、类型与允许的取值，但不能代替真实文件和权限检查。

一次闭环分五步：[^调用接口]

| 步骤 | 责任方 | 实际发生什么 |
| --- | --- | --- |
| 1 | 应用向模型提供工具 | 说明工具用途、参数契约及本轮任务 |
| 2 | 模型向应用提出调用 | 返回工具名、参数及调用编号；此时还没有读取文件 |
| 3 | 应用检查并调度 | 完整解析参数、校验工具和材料范围、检查权限，再执行本地读取或转调服务工具 |
| 4 | 应用回传结果 | 返回真实内容或明确失败，并对应原调用编号 |
| 5 | 模型根据结果继续 | 解释取得的材料，或提出下一次请求；缺内容时不能假装已经读到 |

回传结果还要真正进入后续模型请求。应用只在自己的日志里保存了内容，却没有交给模型，不能据此认定模型已经看到；任务与必要工具结果的消息传递也是应用的责任。[^基础资料]

第3步才触及文件或服务。第2步中的“请求读取乙”是模型生成的行动意图，不是执行结果。只给模型一个工具名称，也没有让文件自动进入上下文。

应用收到参数后，应完整解析并按已有契约验证。不能因为一段字符串里碰巧出现“乙”，就跳过格式和范围检查；也不能替模型猜一个新字段名或把未知材料编号修成自己认为合适的值。

即使参数满足Schema，仍有不同问题要分别检查：乙文件是否存在，执行方是否有读取权限，实际返回是否对应乙，以及条款是否适用于当前日期和对象。

**结构合格只说明请求符合约定，不证明事实、授权或结果**。只有应用真正执行并返回内容，后续判断才有新的证据来源。

## 三、Function Calling与MCP分别连接哪两方

前面的五步里，模型与应用需要一种表达工具请求和返回结果的接口。Function Calling就是这一段的机制：应用提供工具定义，模型产生结构化请求，应用按请求执行并送回结果。[^调用接口]

如果执行的是应用中已有的本地函数，应用检查后直接调用即可。不需要为了读取一次文件，必定另建一个MCP服务。

另一种情况是条款由服务提供。应用中的MCP客户端连接服务端，发现可用工具，再发送服务调用并取得返回。**MCP主要规范应用与服务能力之间的连接**；它与模型侧的Function Calling可以前后衔接。[^服务接口]

| 路线 | 实际读取在哪里发生 | 应用要衔接什么 |
| --- | --- | --- |
| 本地工具 | 应用调用本地读取实现 | 模型请求、参数与权限检查、本地返回 |
| MCP服务工具 | 服务端工具实现读取 | 模型请求与服务工具契约映射、MCP请求与返回、模型结果回传 |

这里的“服务端”是协议角色，可以运行在本机，也可以部署在其他机器；不要仅凭这个名称推断资料一定离开本机。真实数据去向应按连接和实现核对。

两段接口的分工可以画成：

```mermaid
flowchart LR
    A["模型：提出调用，解释结果"] <-->|Function Calling| B["应用：解析、检查与调度"]
    B <-->|本地调用与返回| C["本地工具：实际读取"]
    B <-->|MCP客户端连接| D["MCP服务端工具：实际读取"]
```

MCP还可以提供资源和提示模板，并不只有工具。本阶段关注工具支路：按课程引用的2025-06-18固定工具规范，客户端用`tools/list`取得精确工具名和`inputSchema`，再通过`tools/call`调用，参数放在`params`下的`name`与`arguments`中。[^服务接口]

应用不能直接把一套外层消息当成另一套协议。它需要将模型请求映射到真实服务工具，再把执行结果对应回原模型调用。接口接通解决连接问题，不自动带来业务授权、路径限制、沙箱或独立验收。

## 四、两套编号用来配对，失败也要原样讲清

### 模型调用与MCP请求各有自己的编号

课程用OpenAI Responses接口说明模型侧字段。模型输出中的`type: function_call`表示调用项，`name`表示工具名，`arguments`是JSON编码的参数，`call_id`用于将结果配回这次调用。应用回传结果使用`type: function_call_output`，保留相同的`call_id`。[^调用接口]

MCP的JSON-RPC请求另有`id`，用于配对客户端与服务端的一次协议请求。这与模型侧`call_id`承担不同角色，不是协议自动共用的一套号码。[^服务接口]

本例不编造实际编号值。运行时应读取真实编号并保留对应关系：

```text
模型请求读取甲：甲这次调用的原call_id
模型请求读取乙：乙这次调用的原call_id

若转调MCP：另外记录相应JSON-RPC请求id与返回
回到模型时：甲的结果对应甲，乙的结果对应乙
```

假设应用把乙原文配到甲的`call_id`上，最终答案却碰巧正确。这次接口仍然不合格：过程记录已经声称甲调用取得了乙内容，后续模型和审计都可能沿错配继续。

所以需要两项检查：编号是否正确对应，返回材料是否与该请求一致。只把号码抄对，也不能证明读取的是目标材料。

这些字段限定于本文引用的Responses与固定MCP规范。Claude Code的一个客户端抓包案例采用`tool_use`和`tool_result`，以`tool_use_id`对应原工具调用；它展示相似的职责交接，却不是Responses外层格式，不能混着发送。[^客户端案例]

### 连接成功与读取成功分开判断

若工具返回“文件不存在”，应用应按对应调用回传失败。模型现在知道读取失败，而不是知道了那份材料的内容；不能继续生成“根据已读乙2”的判断。

固定MCP工具规范区分两类错误：协议错误通过JSON-RPC错误返回；工具执行错误可以在工具结果中用`isError: true`表示。正文内容通常在`result.content`里，应用需要识别结果性质并按模型接口回传。[^服务接口]

这时可以确认的事情有层次：

| 已发生的事情 | 还不能推出什么 |
| --- | --- |
| MCP连接建立 | 工具已执行或内容已取得 |
| 调用请求已发出 | 服务端已经完成目标动作 |
| 返回了明确错误 | 已得到所请求的条款内容 |
| 编号配对正确 | 材料真实、条件适用或业务目标完成 |

**结果回传要包含成功内容，也要包含真实失败**。把失败改写成“读取成功”，会给下一轮制造不存在的证据；丢掉错误，又会让系统失去决定继续或停止的依据。

一次闭环现在清楚了。复杂任务需要重复它，但下一次调用应由真实结果决定，这就是第20课接入的地方。

## 五、ReAct让下一步跟着观测走

ReAct是Reasoning and Acting的组合，将判断与行动交错组织。动作获得环境信息，新的观测再影响后续判断。原论文讨论了这种交错方式；这里用课程案例解释职责，不沿用其实验提升数字。[^行动循环]

先看一次只读问答的教学轨迹：

| 轮次 | 本轮行动理由摘要 | 请求与实际执行 | 真实观测 | 下一步 |
| --- | --- | --- | --- | --- |
| 1 | 确认购买规则版本 | 请求读取甲，应用检查后实际读取 | 甲有效至2025-05-31 | 主问题在2025-06-12，继续查替代规则 |
| 2 | 需要乙的当前条款 | 请求读取乙 | 超时，尚未取得内容 | 不判断乙的凭证条件，先确认请求状态 |
| 3 | 取得完整乙依据 | 在允许继续的条件下重新读取乙并得到返回 | 乙1、乙2、乙3及生效说明 | 对照期限、拆封和凭证 |
| 4 | 必要事实与依据已齐 | 形成有限问答结果 | 与原条款逐项核对通过 | 问答结束，未创建受理记录 |

表中理由是外显教学摘要，不声称读取模型完整隐藏推理。读到甲并发现过期，是真实内容触发下一步；读乙超时后缺内容，则对应判断停住。用词叫不叫Thought，并不决定这条链有没有工作。

它可以简写为：

```text
判断当前缺什么 → 提出工具请求 → 应用执行并回传
              → 根据真实观测更新判断 → 再行动或结束
```

超时以后，先检查是不是仍有同一请求运行中。如果仍在运行，就等待或处理这个请求，避免重复发起；如果已结束且没有乙内容，才按已有的有限重试规则使用精确已知材料继续。达到上限仍无内容，应报告缺证并停止对应判断，不凭猜测换文件名。

这里模拟的是读取任务。写入等有副作用的操作，还需要另外检查未知执行状态和安全重复契约，不能直接照搬读取的重试方式；下一阶段会展开这些恢复责任。

取得完整乙以后，可以形成主问题答案：

> 按2025-06-12的购买申请，适用乙。第10天且未拆封符合乙1，含订单号的电子凭证符合乙2，因此满足展示的申请条件。本任务只做解释，没有创建记录或执行退款。

如果还只有乙1，就不能断言凭证合格；若用户只说“电子凭证”而没说明订单号，也应补问事实。循环次数不能补出这些未知信息。

反过来，连续写三次“我再找找”，却没有新的工具请求、返回、明确状态检查或产物，只是重复叙述。判断进展应看获得了什么新证据、做成了哪一步，而不是数出现了多少次行动口吻。

**ReAct的关键是行动、观测与下一步之间的真实联系**。工具可以取得资料，也可能失败，模型必须依据实际返回继续，不能把计划中的观测当成已经发生。

## 六、步骤变多时，在小循环外加一份可变的计划

现在进入另一个明确授权的教学场景。用户在前述核对基础上提出：

> 先核对当前购买申请；如果满足展示的申请条件，为目标申请创建一条待受理记录并验收。不授权退款或外发。

这份新增要求才允许进入条件性的创建流程。最初只读任务没有这个授权，工具连接或“可申请”结论都不能自行把它补出来。

可以先列一个有依赖的外层计划：

| 计划步骤 | 依赖什么 | 应留下什么 |
| --- | --- | --- |
| 取得适用材料 | 实际条款与版本信息 | 能回查的原文与位置 |
| 核对条件 | 当前事实与完整规则 | 日期、对象、期限、拆封及凭证的逐项判断 |
| 创建一条待受理记录 | 条件满足、目标准确、授权有效且执行检查通过 | 实际调用、返回和状态证据 |
| 验收并交付 | 当前完整存储与过程记录 | 对象、状态、依据、唯一性与有无越权的结果 |

Plan-And-Execute将显式计划与当前步骤的执行分开。执行器完成“取得材料”时，内部仍可以采用第五节的ReAct小循环：先读甲、遇到过期、转查乙、处理超时。两者作用层级不同，可以组合。[^计划执行]

Plan负责说明步骤和依赖，Re-Plan根据用户问题、已有计划与真实执行记录，决定怎样调整剩余步骤，或在任务已经能够回答时返回最终结果。本课程采用这套职责口径，不把它写成所有框架的统一分类。

计划也不能证明某一步已经完成。写着“取得乙”，实际只有超时，就应保留缺证；写着“建立记录”，也不能替代真实存储结果。

### 创建以前，用户补充“其实已经拆封”

设新增事实在创建尚未发生时到达。原来的未拆封事实被用户纠正，当前依据仍为乙1、乙2、乙3。

这时，新的判断是：乙1要求未拆封，乙3排除已拆封的这条退货申请路径。原计划的“条件满足后创建待受理记录”不再成立，应撤回创建路径，改为解释乙3的维修核验边界，并报告本次没有创建。

不能为了把清单全部打钩继续创建，也不能把“可转维修核验”写成“维修已经安排”或“退款批准”。用户授权的条件性创建与真实条件要一并检查，维修动作也没有自动获得授权。

若新事实是在动作已经发出以后才到来，就不能照本例宣称“尚未创建”。需要先查询当前实际状态并处理已发生的影响，不能靠改计划让历史动作消失。该恢复问题承接下一阶段，不在这里假定远端已回滚。

### 缺资料与新增否定事实，停止理由不同

乙读取失败时，是缺少规则依据，相关判断待核验；已取得乙而用户改为已拆封时，是现有依据与事实明确不支持原创建路径。

前者需要补证或报告资料不足，后者需要按乙3调整结论与计划。把所有阻塞都写成“我继续尝试”，会掩盖已经应该停止的动作。

计划使多步任务可观察，观测使计划能够改变。两者合作，才不会把用户最初一句话冻结成必须完成的旧路线。

## 七、重规划决定怎么走，检查器确认是否完成

到了交付点，Re-Plan说“工作已经完成”，还需要独立标准和可信产物来支撑。重规划器与Checker的职责分别是：

| 角色 | 主要输入 | 要作出的判断 |
| --- | --- | --- |
| Re-Plan | 当前任务、计划、执行记录与新事实 | 下一步做什么、撤回什么、是否已能形成回答 |
| Checker | 原始条款、明确成功标准、实际产物与状态 | 结果是否满足目标，过程是否违反约束 |

两种角色可以由同一个程序分别承担，也可以使用不同实现，但责任与证据必须明确。增加一个叫Re-Plan的第二模型，不自动构成独立验收；若它只听执行者说“成功”，仍没有实际状态证据。

对只读主问题，Checker要核对乙是否真正进入本轮输入、期限与未拆封是否引用乙1、凭证是否引用乙2、订单号限定是否保留，以及有没有把问答写成动作完成。

对新增动作任务，仅在真实创建路径发生后，Checker才检查目标申请与订单、一条待受理记录、乙1乙2依据及授权范围。工具回执或调用编号都不能代替这些状态检查。本篇没有执行这个创建服务，只说明验收应检查什么。

这与第六阶段相接：过程记录帮助查错，结果证据支持完成。计划显示的进度也需要具体产物支持。Anthropic的长任务工程文章描述过未充分测试就标记完成的失败，并强调用实际检查验证功能；这个原则不能被简化成“有进度文件就完成”。[^真实验收]

还有一项贯穿两课的边界：计划写了目标目录，不能据此宣布文件工具被限制在目录内。读取、写入与命令实际能访问哪里，需要执行实现和权限来约束。对应ReAct示例的当前整理资料明确指出，任务目录用于提示并不构成沙箱；它是理解流程的实现案例，不是完整生产权限系统。[^计划执行]

## 八、把两课连成一条真正的执行链

回到开头，“我去读取乙”首先要形成明确请求。应用完整解析、检查并调度执行：本地函数直接调用，服务工具则经MCP客户端连接。实际内容或失败按正确编号回到模型，这一次工具闭环才有可核对的来回。

闭环重复时，下一步必须依据观测改变：甲过期就查适用版本，乙超时就处理当前请求和缺证，真实取得乙才核条件。步骤有依赖时，在外层保留计划；新事实否定原条件时，就撤回不再成立的路径，而不是继续把旧清单走完。

```text
任务与工具契约
→ 模型提出请求
→ 应用解析、检查与调度
→ 本地工具或MCP服务实际执行
→ 原编号回传内容或失败
→ 模型根据观测继续或结束
→ 有依赖时调整外层计划
→ 检查器依据实际产物与约束验收
```

这条链将第19课的接口责任与第20课的循环责任放在同一案例里。它不会因为出现了Function Calling、MCP、Thought或Re-Plan这些名称就自动可靠；每个名字都要落到已经发生的请求、执行、返回、判断和验收上。

走完本阶段，应能画出谁提出请求、谁真正读取、两段接口怎样连接，说明参数解析、编号配对与失败回传各自解决什么；也能解释为什么读取失败不能继续断言，为什么已拆封的新事实会改变计划，以及为什么重复进度叙述不能替代新证据。

下一阶段第21—23课将继续处理执行外壳、不同状态的保存恢复，以及长期Loop的跨轮触发。当前任务内能循环，不表示已经具有持久恢复或无人值守能力；这条链还要接上授权、对账、预算、停止与可信状态。
